# 階段 1～3：基礎產物審計（避免冗餘）

進入階段 1～3 時才讀取本檔。目的：可攜到其他專案時，**不重寫、不堆疊**已有的 constitution／rules。

## 共通原則（三階段皆適用）

1. **先讀再寫**：先檢查既有檔案，再決定動作。
2. **已涵蓋 → 標記完成並跳過寫入**（可向使用者簡述既有來源路徑）。
3. **部分涵蓋 → 只補缺口**；若需改寫既有段落，**先詢問**是否合併／修訂。
4. **完全沒有 → 才新建**。
5. **禁止**無故整份覆寫、複製貼上產生平行重複的 rule／constitution 條文。
6. 勿用 `--force` 或等價手段覆蓋使用者已改過的內容，除非使用者明確要求。

---

## 階段 1：Constitution

### 檢查

- `.specify/memory/constitution.md`（或專案慣用的 constitution 路徑）
- 是否已描述：技術棧、後端呼叫／回傳通用格式、分層與品質相關原則

### 判定

| 狀態 | 行為 |
|------|------|
| 已涵蓋本階段所需 | 標記階段 1 完成；**不重寫** |
| 部分涵蓋 | 只補缺的原則／章節；大改先詢問 |
| 不存在或僅空白模板 | 分析系統後寫入 constitution |

### 輸出

- 就緒：沿用既有 constitution
- 否則：寫入／補齊 Speckit constitution 細節

---

## 階段 2：架構長期記憶（rules）

### 檢查

- `.cursor/rules/`（或其他 agent rules 目錄）是否已有架構／慣例相關規則
- 常見主題：專案結構、資料庫、控制器、共用工具、開發慣例

### 判定

| 狀態 | 行為 |
|------|------|
| 主題已有對應 rule 且足夠 | 標記完成；**不新增平行 rule** |
| 缺某主題 | **只新增缺的** rule 檔（或經同意後擴充既有檔） |
| 完全沒有 | 分析架構後建立精簡 rules |

### 輸出

- 精簡 rules，必要時指向 constitution；避免與 constitution 全文重複貼上

---

## 階段 3：API 開發規範

### 本 skill 執行約束（跑階段 4～8 時必須遵守）

無論是否寫入專案長期記憶，執行本 skill 的 API／MCP 實作時皆須遵守：

1. 所有新建程式碼皆須獨立儲存於新檔案，不可汙染既有內容。
2. 使用者驗證、紀錄查詢，都須使用既有函式。
3. 資料庫規格也不可變更；僅另外建立 API 接口，並使用原邏輯組建。
4. ViewModel 如果有找到既有可用的則沿用。
5. 如果發現共通架構程式有誤或效率不佳，不可直接修改，應詢問是否調整。

> 以上偏「既有系統薄封裝 API」。若目標專案性質不同（例如允許 schema 變更），**先詢問使用者**是否調整約束，再繼續階段 4。

### 寫入長期記憶（constitution／rules）前

| 狀態 | 行為 |
|------|------|
| 既有 constitution／API rule 已涵蓋同等約束 | **不重複寫入**；階段 4 起直接引用既有規範 |
| 部分涵蓋 | 只補缺口；或詢問是否合併進既有 Principle／rule |
| 完全沒有 | 才將規範寫入 Speckit（完整）+ 精簡 rule（指向 constitution） |

### 理想運作

- Speckit：完整細節
- Rule：精簡，並指向 constitution 的核心規範
- **同一約束不要在多個 rule 檔各寫一份全文**
